# Local operation and future free hosting

No deployment has been performed. Local Windows commands are in README.md. The API binds to loopback; Vite is LAN-accessible and proxies relative /api so a phone does not call its own localhost. PostgreSQL binds only 127.0.0.1. Never port-forward a development server to the public internet.

Future target considered on 11 October 2026: Cloudflare Pages static frontend, Render Free Node/Fastify/Socket.IO backend, Supabase Free PostgreSQL. There are no subscriptions or created accounts. Official references: [Render Free](https://render.com/docs/free), [Supabase pricing](https://supabase.com/pricing), [Cloudflare DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/).

Render Free sleeps after inactivity, uses an ephemeral filesystem, and has a monthly shared runtime allowance. Free Render Postgres expires and is not selected. Supabase has limited database storage/egress and inactive projects can pause. Match snapshots/events/clock anchors and auth sessions therefore belong in PostgreSQL, not backend RAM/files. Persist before acknowledging moves; display reconnect/cold-start errors honestly. Active-match timeout policy must survive server sleep and be tested in stage 2. Cap retention of event histories/notifications and inspect DB size; reject new work if Free limits are reached instead of enabling paid capacity.

Cloudflare Workers + SQLite Durable Objects + D1 is a viable future Free alternative for capped traffic, with per-match actors, hibernating WebSockets and SQLite storage. It requires a new server/storage adapter, a runtime-safe password hashing strategy, and a different WS transport rather than simply running this Node app unchanged. Node/PostgreSQL remains the first implementation; no promise of guaranteed free unlimited hosting or zero-effort migration.

Critical launch tasks: same-origin /api and WS reverse proxy (or a reviewed domain plan) for cookies across Pages/Render; CSP/security headers on Pages; exact Origin/proxy configuration; TLS and DB certificate verification using provider connection guidance; migrations in a controlled release step; verified zero-cost SMTP provider (not yet chosen); recheck limits. Paid services, custom-domain purchase, and provisioning require user permission. Rate limiting per real client IP behind the chosen proxy must be explicitly tested.

Docker Compose currently includes local PostgreSQL and Mailpit. Embedded-postgres is optional development tooling only; its wrapper's latest registry tag is beta, the binary reports PostgreSQL 18.4. Docker uses PostgreSQL 17. Both must be exercised in CI before production. Production server build is dist/server/index.js; frontend build is dist/web, configured with SPA fallback at its eventual host. npm start serves API only. CI should migrate a temporary PostgreSQL service, run check + E2E and scan secrets; a local workflow is prepared in .github/workflows/check.yml, but has not run on GitHub. The frontend includes a Pages _headers template; validate it with the final same-origin API/WS routing. Publication still requires user authorization.

Operational tooling is now implemented and locally exercised: native transactional backup/restore, isolated recovery test and retention dry-run/apply. Production requires provider validation; no automated cloud backup schedule or resources exist. TLS uses verified certificate/hostname and a configurable CA file. Only explicit verified proxy CIDRs may be trusted. See OPERATIONS.md.
