# MASTER PROMPT — Створення професійної онлайн-платформи настільних стратегічних ігор

## 1. Твоя роль

Ти — Senior Full-Stack Software Engineer, Software Architect, UI/UX Designer та Security Engineer із досвідом понад 10 років у створенні сучасних вебзастосунків, багатокористувацьких платформ і систем реального часу.

Твоє завдання — спроєктувати та реалізувати з нуля професійну, сучасну, адаптивну онлайн-платформу стратегічних настільних ігор.

Це не просто демонстраційний сайт і не набір статичних сторінок. Потрібен реальний Full-Stack продукт, який працюватиме локально, а згодом буде опублікований у відкритому GitHub-репозиторії та розгорнутий в інтернеті.

Проєкт має бути достатньо якісним, щоб його можна було використовувати як вагому роботу в портфоліо Full-Stack Developer.

**Головна вимога:** якість архітектури, логіки, дизайну, зручності та безпеки важливіша за формальну кількість реалізованих функцій.

Не використовуй фальшиві кнопки, вигадані серверні відповіді, статичні рейтинги, декоративні форми авторизації або імітацію мультиплеєра замість реальної роботи.

Якщо певна функціональність не завершена, чітко позначай її стан, а не видавай за готову.

## 2. Назва, брендинг та концепція

Робоча назва — BoardArena. Це тимчасова технічна назва, а не остаточний бренд.

Перед реалізацією:

1. Придумай 5–8 коротких, сучасних, оригінальних назв.
2. Назва має легко вимовлятися українською та англійською.
3. Вона повинна асоціюватися зі стратегією, інтелектом, змаганнями, майстерністю або настільними іграми.
4. Уникай банальних назв на кшталт ChessOnline, GamesHub, ProChess, GameZone.
5. Не копіюй назви Chess.com, Lichess, PlayStrategy або інших платформ.
6. Якщо доступний інтернет, перевір потенційні конфлікти назв, торговельних марок і доступність доменів. Якщо перевірка неможлива — зазнач це.
7. Запропонуй найкращий варіант і використовуй його як попередній бренд, щоб надалі можна було легко перейменувати платформу.

Також розроби цілісну дизайн-систему бренду: логотип, кольори, типографіку, стиль іконок, кнопок, карток, анімацій і маскота.

**Концепція:** міжнародна онлайн-платформа стратегічних настільних ігор українського походження, яка поєднує гру, навчання, змагання, соціальну взаємодію та прогрес гравця.

Основні мови: англійська й українська.

## 3. Обов'язкові університетські вимоги

Цей проєкт також є навчальним завданням із веброзробки.

Мінімальні вимоги викладача:

- Щонайменше 3 повноцінні сторінки з різним наповненням.
- Адаптивна верстка для ПК та смартфонів.
- Використання HTML, CSS, JavaScript.
- Використання CSS Grid.
- Використання Flexbox.
- Обов'язкові CSS media queries для адаптивних точок зламу.

Це лише мінімальні вимоги. НЕ обмежуй продукт трьома сторінками.

Забезпеч щонайменше головну сторінку, каталог ігор та окремі сторінки кожної гри. Додатково реалізуй профілі, рейтинги, навчання, друзів, налаштування й інші функціональні розділи.

Вимоги до верстки:

- Mobile-first.
- Семантичний HTML5.
- CSS Grid для основних макетів і каталогів.
- Flexbox для панелей навігації, форм, тулбарів і компонентів.
- Явні CSS media queries у вихідних CSS-файлах.
- Адаптація орієнтовно для 320–375, 390–430, 768, 1024, 1440 та 1920 px.
- Вибір точок зламу за потребами контенту, а не лише за популярними розмірами пристроїв.
- Жодного випадкового горизонтального прокручування.
- Підтримка портретної та альбомної орієнтації.
- Збереження повної функціональності на сенсорних екранах.

Не використовуй виключно utility-класи Tailwind як заміну явним CSS Grid, Flexbox і media queries. Для навчальної перевірки в коді повинні бути зрозумілі CSS-правила.

Підготуй окремий файл `docs/COURSE_REQUIREMENTS.md`, у якому буде пояснено, як виконані вимоги викладача, де використовуються CSS Grid/Flexbox, які медіазапити реалізовані та які сторінки демонструють різний контент.

## 4. Рекомендований технологічний стек

Вихідні побажання: HTML, CSS, JavaScript, React.

Рекомендована архітектура:

Frontend:

- React.
- TypeScript.
- Vite.
- React Router.
- CSS Modules або добре організований звичайний CSS.
- CSS Custom Properties.

Backend:

- Node.js із TypeScript.
- Express або Fastify — вибери один, обґрунтувавши вибір.
- Socket.IO для real-time комунікації.
- REST API для звичайних операцій.
- Серверна перевірка всіх ігрових дій.

Database:

- PostgreSQL.
- Prisma або Drizzle ORM із міграціями.
- Нормалізована схема бази даних.

Інфраструктура:

- Docker Compose для локальних сервісів.
- GitHub Actions для подальшого CI.
- Vitest для модульних тестів.
- Playwright для E2E-тестування.
- ESLint, Prettier, TypeScript strict mode.
- Zod або інший надійний валідатор API-даних.

Redis додавати лише там, де це виправдано — наприклад, для черг, розподілених матчів або масштабування WebSocket. Не ускладнюй початкову версію без потреби.

Використовуй актуальні стабільні версії бібліотек. Перед інтеграцією перевір документацію, сумісність та ліцензії. Не вигадуй API сторонніх пакетів.

Архітектура має бути модульною, придатною для розширення до десятків різних ігор.

## 5. Три обов'язкові повноцінні ігри

Початкова версія платформи повинна включати три гри:

1. Chess — класичні шахи.
2. Checkers — шашки.
3. Onitama або оригінальну тактичну гру зі схожим принципом обміну картками рухів.

Кожну гру потрібно реалізувати як окремий модуль із власними правилами, рушієм, ботом, навчанням, рейтингами та інтерфейсом.

При цьому авторизація, кімнати, система друзів, профілі, матчмейкінг і статистика повинні бути спільними для всіх ігор.

### 5.1. Chess

Реалізуй повноцінну гру за стандартними правилами шахів.

Обов'язково:

- Початкова розстановка.
- Правильні ходи всіх фігур.
- Взяття фігур.
- Шах.
- Мат.
- Пат.
- Рокірування.
- En passant.
- Перетворення пішака.
- Нічия за правилами.
- Повторення позицій.
- Правило 50/75 ходів там, де застосовне.
- Недостатній матеріал.
- Контроль часу.
- Здача.
- Пропозиція та прийняття нічиєї.
- Історія ходів.
- Перегляд попередніх ходів після партії.
- FEN і PGN для збереження та експорту.
- Переворот шахівниці.
- Підсвічування допустимих ходів.
- Позначення останнього ходу.
- Індикація шаху.
- Повідомлення про завершення гри.

Для перевірки правил розглянь chess.js. Для візуалізації — react-chessboard або власний компонент.

Не переписуй складні шахові правила з нуля, якщо надійна бібліотека вже вирішує це завдання.

Додай режими гри:

- Проти бота.
- Проти друга.
- Приватна кімната.
- Випадковий онлайн-суперник.
- Рейтингова партія.
- Нерейтингова партія.

Часові контроли, наприклад:

- Bullet: 1+0.
- Blitz: 3+0, 3+2, 5+0.
- Rapid: 10+0, 15+10.
- Без таймера для дружніх навчальних партій.

Контроль часу має виконуватися сервером, а не залежати від браузера користувача.

### 5.2. Checkers

Реалізуй повноцінні шашки.

Перед розробкою досліди основні різновиди правил і зафіксуй обрану систему.

Для першої версії рекомендую звичні в Україні шашки 8×8, з можливістю додати міжнародні шашки 10×10 пізніше.

Правила вибраного різновиду повинні бути реалізовані повністю:

- Звичайне пересування.
- Обов'язкове взяття.
- Серії взяттів.
- Перетворення на дамку.
- Правила пересування дамки.
- Завершення партії.
- Нічиї.
- Коректне визначення переможця.

Особливо уважно перевір правила взяття назад, пріоритету взяттів і перетворення під час серії взяттів — вони різняться між варіантами.

Передбач розширення для різних правил шашок без переписування спільного мультиплеєра.

Створи компетентного бота з кількома рівнями складності, наприклад через minimax з alpha-beta pruning.

### 5.3. Onitama / оригінальна тактична гра

Спочатку вивчи офіційні правила Onitama: поле 5×5, майстер, учні, картки рухів, обмін картки з відкритою спільною карткою, захоплення майстра та перемога через храм.

Це комерційна настільна гра. Перевір ліцензійні та юридичні обмеження.

Не використовуй без дозволу оригінальні ілюстрації, логотип, оформлення карт, графічні ресурси або інші захищені матеріали.

Якщо права на комерційне використання назви чи конкретних матеріалів не підтверджені, реалізуй оригінальну авторську тактичну гру з власною назвою, оформленням і власними варіаціями механіки.

Технічні вимоги:

- Повністю робоча механіка.
- Коректна перевірка ходів.
- Візуалізація доступних напрямків.
- Обмін картками рухів.
- Визначення переможця.
- Навчання.
- Гра проти бота.
- Онлайн-матчі.
- Власний рейтинг.

Зроби цю гру візуально особливо цікавою, але без надмірних ефектів.

## 6. Архітектура ігрових рушіїв

Створи абстракцію `GameEngine` або еквівалент.

Кожен рушій повинен підтримувати:

- Створення початкового стану.
- Отримання допустимих дій.
- Перевірку дії.
- Застосування дії.
- Визначення поточного гравця.
- Визначення завершення партії.
- Серіалізацію і десеріалізацію стану.
- Відтворення історії дій.
- Валідацію стану після відновлення.

Сервер є авторитетним джерелом стану гри.

Клієнт може показувати попередню анімацію ходу, але тільки сервер вирішує, чи допустимий цей хід.

Передбач захист від:

- Ходів поза чергою.
- Повторного надсилання однієї дії.
- Підроблених результатів.
- Неавторизованого керування чужою партією.
- Маніпуляцій таймером.
- Гонок стану.
- Неправильного відновлення після втрати зв'язку.

Для ігрових подій використовуй чітко типізовані контракти та ідентифікатори дій для ідемпотентності.

Обов'язкові можливості:

3. Підключення друга за посиланням.
4. Вибір гри й параметрів.
5. Розподіл сторін.
6. Синхронізація дій.
7. Відображення часу.
8. Перевірка сервером усіх ходів.
9. Обробка відключення суперника.
10. Автоматичне перепідключення.
11. Відновлення актуального стану партії.
12. Завершення матчу.
13. Збереження результату.
14. Повторна партія.
15. Відображення помилок з'єднання.

Додай режим гостя для приватних нерейтингових матчів. Для рейтингових матчів необхідна авторизація.

## 8. Боти та одиночна гра

Кожна з трьох ігор повинна мати робочого бота.

Рівні складності:

- Beginner.
- Intermediate.
- Advanced.
- За можливості Expert.

Для шахів досліди можливість використання Stockfish у Web Worker або на сервері.

Врахуй GPLv3 та всі ліцензійні зобов'язання, якщо Stockfish буде інтегрований.

Бот не повинен блокувати основний UI-потік.

Для шашок і третьої гри розглянь minimax, alpha-beta pruning та евристичні оцінки позицій.

Режими проти бота:

- Звичайна партія.
- Навчальна партія.
- Тренувальний сценарій.

Боти повинні мати реальні відмінності у складності.

Результати ігор проти ботів не повинні впливати на конкурентний рейтинг.

## 9. Інтерактивне навчання

Замість великих сторінок із сухими правилами створюй навчання через практику.

Для кожної гри необхідні:

- Коротке знайомство.
- Покрокові інтерактивні уроки.
- Візуальні демонстрації.
- Підсвічування правильних дій.
- Пояснення помилок.
- Маленькі практичні завдання.
- Навчальна партія проти бота.
- Відстеження проходження уроків.

Наприклад, для шахів:

1. Навчи рухати пішака.
2. Навчи рухати туру.
3. Поясни інші фігури.
4. Покажи взяття.
5. Продемонструй шах.
6. Поясни, як захищатися від шаху.
7. Покажи мат на простій позиції.
8. Навчи спеціальних правил.
9. Проведи першу навчальну партію.

Завдання мають виконуватися безпосередньо на інтерактивному полі.

Користувач не повинен просто натискати «Далі» й проходити урок без виконання потрібних дій.

Передбач пропуск навчання, повторення уроків і доступ до довідки під час гри.

## 10. Маскот — оригінальний персонаж платформи

Придумай власного впізнаваного персонажа, який стане частиною бренду.

За рівнем продуманості орієнтуйся на якісні освітні застосунки, але НЕ копіюй сову Duolingo чи інших відомих персонажів.

Вимоги:

- Оригінальний силует.
- Виразний характер.
- Відповідність тематиці інтелектуальних ігор.
- Приємні кольори.
- Простота сприйняття на маленькому екрані.
- Декілька емоцій і станів.
- Ненав'язлива анімація.

Маскот може:

- Вітати нового гравця.
- Пояснювати правила.
- Реагувати на виконання уроку.
- Вітати з перемогою.
- Підказувати наступний навчальний крок.
- Показувати інформацію про щоденну серію.
- Допомагати освоїти інтерфейс.

Розроби його як набір оригінальних SVG-компонентів з CSS-анімаціями або іншим відповідним легким способом.

Не підміняй маскота випадковим emoji чи стороннім зображенням.

Не обіцяй складної анімації, якщо немає потрібних ресурсів. Краще якісна проста SVG-анімація, ніж незавершений 3D-персонаж.

Не використовуй маскота у спосіб, що заважає партії або перекриває ігрове поле.

Дотримуйся `prefers-reduced-motion`.

Захист паролів через Argon2id або інший перевірений алгоритм.

Не зберігай паролі у відкритому вигляді.

Використовуй безпечні HttpOnly cookies та серверне керування сесіями.

Передбач захист від CSRF, session fixation, credential stuffing та brute-force атак відповідно до обраної архітектури.

Для локальної розробки налаштуй Mailpit або подібний інструмент перевірки email без реального відправлення листів.

У продакшені email-підтвердження й відновлення пароля повинні працювати через налаштований SMTP/email-сервіс.

Не видавай локальну тестову доставку листів за реальну продакшен-інтеграцію.

Google OAuth можна передбачити архітектурно, але не вигадуй фіктивну інтеграцію без необхідних облікових даних.

## 29. Майбутній хостинг

Зараз НЕ розгортай сайт.

Але спроєктуй архітектуру так, щоб потім його можна було без значних змін опублікувати.

Розглянь:

- Cloudflare Pages або Vercel для frontend.
- Railway або Render для Node.js/WebSocket backend.
- Керований PostgreSQL.
- Environment variables у налаштуваннях хостингу.
- HTTPS/WSS.
- Міграції бази.
- Production-логи.
- Health checks.
- Резервне копіювання.

Підготуй інструкцію з розгортання, але не виконуй deployment без підтвердження.

Не покладайся на ефемерну пам'ять сервера для довготривалого збереження матчів.

Критична вимога до інфраструктури: платформа повинна мати можливість повністю безкоштовного публічного розгортання із щомісячними витратами 0 USD. Не використовуй сервіси, що обов'язково потребують платної підписки після пробного періоду. На першому етапі орієнтуйся на Cloudflare Pages, Render Free і Supabase Free. Врахуй засинання безкоштовного сервера, перепідключення користувачів, збереження стану матчів та безкоштовні ліміти бази даних. Перед початком реалізації backend оціни альтернативну архітектуру Cloudflare Workers + Durable Objects + D1. Обирай архітектуру з урахуванням нульової вартості, підтримки онлайн-партій, безпеки та зручності подальшої розробки. Не активуй платні тарифи й не створюй ресурси, які можуть спричинити списання коштів, без окремого дозволу.

- Сервер перевіряє ігрові дії.
- Боти функціонують.
- Працюють інтерактивні навчальні сценарії.
- Працюють рейтинги та збереження результатів.

- README та документація відповідають реальному стану проєкту.

Якщо не всі критерії виконані, чітко повідомляй, що реалізовано, що протестовано, що потребує доопрацювання та які є блокери.
